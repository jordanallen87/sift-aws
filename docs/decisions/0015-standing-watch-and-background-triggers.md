# 0015 — Standing Watch and background triggers

**Date:** 2026-09-07
**Status:** Accepted
**Builds on:** ADR 0001 (runtime/storage/heroes), ADR 0006 (WebMCP read/write/presentation/execution split), ADR 0012 (deterministic scoring and insights)

## Context

`docs/hackathon-enhancements.md` names the product's one honestly-disclosed structural weakness: nothing in Sift decides, on its own, that work needs doing. Every investigation today starts from a person clicking a button. The Everyday track's defining sentence — agents that "run quietly in the background and only ping you when there's a real decision to make" — describes a capability Sift does not have, and `docs/hackathon-enhancements.md` §5 confirms this by direct grep: `setInterval|scheduler|watch` returns nothing but the model-provider pacing delay and the SSE module. There is no background loop anywhere in the runtime.

Before proposing a design, the addendum to that document (`docs/hackathon-enhancements.md`, "Addendum, 2026-09-07 evening") spiked the four Strands SDK primitives a background-triggered feature would plausibly need, against this project's own real scripted `Model` test double, and recorded the results in `docs/research/strands-spikes.md`. All five spikes pass (`HumanInTheLoop` interrupt/resume across a genuine process restart, `CedarAuthorization`, an in-process `A2AExpressServer`/`A2AAgent` round trip, `LLMSteeringHandler` with a custom `SteeringContextProvider`, and `MemoryManager`+`TestMemoryStore`), and none needs a live model call to prove out. This ADR is written against those confirmed results, not against assumed SDK behavior — where a spike's own "gotchas" section records an exact API shape (`agent.invoke([new InterruptResponseContent(...)])`, not a `resume()` method; a Cedar deny reaching the model as a `toolResultBlock` with `status: 'error'`, not a thrown exception; `LLMSteeringHandler`'s `'guide'` outcome cancelling the tool call it gates, not annotating it), this ADR uses that shape.

The same research pass found four concrete gaps that become correctness bugs the moment anything other than a click can start a run (`docs/hackathon-enhancements.md` §A, "What our runtime already has" / "What it does not have"):

1. **No per-case run guard.** `RunService.requestInvestigation` (`apps/agent/src/services/run-service.ts`) already starts an engine detached from the HTTP request — `void runInSpanScope(runId, () => this.deps.engines?.[snapshot.pack.id]?.trigger(...))` — so background execution is not new work. But nothing prevents two runs on the same case interleaving. A person clicking a control while a watch fires is the first thing that will happen on camera.
2. **No case-list read surface.** `GET /api/cases/:caseId/events` (`apps/agent/src/routes/events.ts`) is the only SSE stream, and it is scoped to one case. `apps/agent/src/routes/cases.ts` exposes `POST /api/cases/demo`, `POST /api/cases`, `POST /api/cases/energy-bill-feed-check`, and `GET /api/cases/:caseId` — no endpoint returns more than one case. A case list showing "3 watched, 1 needs you" has no data source.
3. **No read marker.** Nothing records what a person has already seen. A "since you were away" digest cannot be built without one.
4. **Duplicate `Clock` ports.** Confirmed directly in `packages/core/src/*.ts`: `attributes.ts`, `evidence.ts`, and `policy.ts` each declare their own structurally-identical `interface Clock { now(): string }`, and a fourth file, `packages/core/src/ports.ts`, already exists specifically to be the canonical replacement — its own header comment records that a prior integration pass added it, decided the three duplicates were "harmless... left as-is," and re-pointed only `index.ts`'s barrel export at it. **This corrects the originating proposal**, which described "two identical `Clock` interfaces (`attributes.ts` and `evidence.ts`)": there are three duplicate declarations, not two, and a canonical fourth (`ports.ts`) already exists and is already `packages/core`'s intended import surface for new code — it is simply not yet adopted by the three older files that predate it. See Decision 10 below for what this ADR actually requires as a consequence.

`docs/hackathon-enhancements.md` §1 and its addendum §D also record four architecture decisions made before this ADR was written, by the person directing the build, in response to specific risk the team was not willing to take on this close to a deadline. Sections 1–4 below record those decisions, their rationale, and their consequences; they are not re-opened here. Everything after them is this ADR's own design for the surface area those four decisions leave open: authority, trigger taxonomy, pack declaration, event vocabulary, the honesty boundary, determinism, and the prerequisites the minimum slice needs before it can ship.

**Pack scope.** The illustrative examples throughout this ADR use the `bid-comparison` pack (`packages/packs/src/bid-comparison.ts`) — its obligations (`bid.scope_normalization`, `bid.price_verification`, `bid.credential_verification`, `bid.schedule_feasibility`, `bid.award_recommendation`), specialists (`scope-analyst`, `price-analyst`, `credential-checker`, `schedule-analyst`), and consequential tool (`propose_award`, gated by policy `bid.award-approval`) are real, already-shipped identifiers, not invented for this document. `docs/hackathon-enhancements.md` §7 is explicit that Standing Watch must not touch `car-purchase` or `home-energy-guardian`: "They are green, baselined, and the versatility beat." This ADR treats that as binding: `bid-comparison` is the only pack this feature is designed to instrument first.

## Decision

### 1. `HumanInTheLoop` composes with `ConsequenceGuard`; it does not replace it

The pack keeps declaring which tools are consequential — that declaration is deterministic, core-owned, unchanged (`ToolDeclaration.effect`, `PolicyDefinition`, `packs-and-routing.md`/`packages/contracts/src/packs.ts`). What changes is the **mechanism** that enforces a pause on a consequential tool call, selected by **where the run originated**:

- A **foreground** run — one a person's click or a WebMCP tool call started while a browser is attached to the case — keeps using `ConsequenceGuard` exactly as it is implemented today (`apps/agent/src/runtime/interventions.ts`). It emits `intervention.confirm` on `beforeToolCall`, the agent process stays live, and the confirmation is answered synchronously (or, in deterministic tests, through `ConsequenceGuardDeps.resolveConfirmation`).
- A **watch-initiated (background)** run has no live consumer to answer a confirm. There is no open SSE connection, no browser tab, possibly no running process by the time a human gets to it — Railway can restart the service, and AgentCore Runtime has a 15-minute idle timeout (Decision 4 below). Spike 1 (`docs/research/strands-spikes.md`) proves the SDK's own answer to exactly this problem: `HumanInTheLoop`'s default mode pauses the agent with `stopReason: 'interrupt'`, the interrupt state round-trips through a real `SessionManager` + `LocalFileStorage` snapshot (the `'session'` preset's field list includes `'interrupts'`), and a **genuinely new** `Agent` instance in a later process resumes it with `agent.invoke([new InterruptResponseContent({ interruptId, response })])`. A watch-initiated run that reaches `propose_award` therefore does not block a process; it persists a pending interrupt, stops, and waits — for minutes, hours, or across a restart — for a human to answer it.

One `ConsequenceGuardDeps.consequentialToolIds`/`forbiddenToolIds` declaration; two intervention handlers, chosen by run origin, both gating the same tool names. Neither handler needs to know the other exists — they are never registered on the same agent instance, because a run has exactly one origin. `strands-adapter.ts`'s existing per-run intervention list construction is the natural seam: it already builds the ordered handler list per run (`strands-runtime.md`, "Interventions and steering"), so selecting `ConsequenceGuard` or `HumanInTheLoop` there, keyed on the run's origin, is additive rather than a rewrite of that construction.

**Consequences.** The tested, baselined foreground confirm path (`ConsequenceGuard`, its scenario assertions, its `resolveConfirmation` fixture hook) is untouched. `HumanInTheLoop`'s interrupt/resume flow is new surface: it needs a durable place to record "case X has a pending background confirmation, since T, for reason R" that the case workspace can read without decoding a Strands session file (see Decision 4 and the Prerequisites section). Two mechanisms answering the same declared consequential-tool boundary means two intervention event shapes reach the runtime telemetry stream for what is, from the pack's point of view, the identical policy fact — `strands-runtime.md`'s "Interventions and steering" is amended (see the spec edits accompanying this ADR) to say this explicitly, rather than leaving an implementer to notice the divergence by reading two source files.

### 2. Cedar authorization is flag-gated, not the default

`ScopeAuthorization` (`apps/agent/src/runtime/interventions.ts`) remains the shipped deny mechanism for undeclared tools, unchanged. Spike 2 proves `CedarAuthorization` works — a `principalResolver` reading `invocationState` correctly permits one agent principal and denies another against the identical tool, and fails closed (denies) when the resolver cannot identify a principal — and it is a materially more legible "policy as data" story for an AWS judge than a hand-written allowlist. It is documented here, and in the accompanying `strands-runtime.md` edit, as a proven AWS-native alternative available behind configuration. It is **not** wired into the hero path.

The reason is risk, not merit: `ScopeAuthorization` is what every existing scenario assertion and visual baseline currently exercises for the deny beat. Rewiring the mechanism that produces "Action blocked" this close to a deadline risks the one thing this build cannot afford to break — a tested, baselined boundary — for a change whose payoff is presentational (a different, arguably better-looking policy substrate) rather than functional (the deny behavior itself does not change). `docs/hackathon-enhancements.md`'s own "What not to do" is direct about this class of risk: touching a green, baselined path for a documentation-shaped win is the wrong trade this week.

**Consequences.** Cedar ships as spike evidence and a documented, config-gated alternative (`SIFT_AUTHORIZATION_MODE=scope|cedar`, default `scope` — named here as the environment variable shape a later task should implement, not implemented by this ADR). No hero scenario, baseline, or submission claim depends on it running. `bid-comparison`'s own real deny example — `price-analyst` must not call `license-lookup` — is exactly the policy spike 2 already proves in isolation (`permit(principal == Agent::"credential-checker", action == Action::"license-lookup", resource); forbid(principal == Agent::"price-analyst", ...)`), so adopting Cedar later requires no new policy design, only wiring.

### 3. Vended LLM steering and `RetrySteering` never contend, because they act in different phases

`RetrySteering` guards tool calls **during** a run — it is registered as an `InterventionHandler` on the orchestrator/specialist agent and evaluates each `beforeToolCall` against the deterministic `ToolLedger` (`strands-runtime.md`, "Retry steering rules"). Vended `LLMSteeringHandler` (spike 4) is used here for **watch triage** — deciding whether a detected change is material enough to justify starting a background run **before** a run exists at all. Triage happens once, at dispatch time, outside any agent's tool-call loop; `RetrySteering` has nothing to guard yet, because no tool call has been attempted.

They can never both fire on one tool call, because they never share a call: triage produces a yes/no plus a note, and only a "yes" produces a run — a run that, once started, is an ordinary bounded orchestrator/specialist execution with `RetrySteering` registered on it exactly as any other run has. The triage agent itself is not gated by `RetrySteering` at all; it is a separate, single-shot `Agent` (spike 4's pattern — `LLMSteeringHandler` builds and invokes its own inner agent per call, with its own model, no shared mutable state) bounded by `BudgetGuard` on a tightened budget (`docs/hackathon-enhancements.md`'s `work.budget: { toolCalls: 12, modelCalls: 6 }` shape, tighter than a foreground run's default bounds in `strands-runtime.md`).

**Consequences.** No new intervention-ordering rule is needed in `strands-adapter.ts`'s per-run handler list, because triage's `LLMSteeringHandler` is never registered on the same agent `RetrySteering` runs on — it gates a *different, smaller* agent (the triage agent), invoked from the scheduler dispatcher, not from inside an orchestrator/specialist run. The accompanying `strands-runtime.md` edit states this as a structural fact ("different agents, different phases"), not a coincidence of current configuration that a future refactor could quietly violate.

### 4. The scheduler is in-process with Express, and all its state lives in SQLite

No `setInterval` holding a JavaScript closure as its only record of a pending obligation. A watch registration, a watch's cursor into its feed, and a pending `HumanInTheLoop` interrupt are each a row: `watches` (one per case × declared watch id: cursor, `lastCheckedAt`, `lastFiredAt`, status), and `pending_interrupts` (one per unresolved background confirmation: run id, watch id, tool name, reason, `createdAt`, and a nullable `resolvedAt`/`response`). On boot, the scheduler rehydrates every active `watches` row and resumes ticking; nothing about "what to watch and how far it got" lives only in a process's memory.

Ticks are **idempotent, keyed by (watchId, cursor)**. A tick reads its feed for entries after the row's current `cursor`, and the cursor advance is committed in the same transaction as any resulting `CaseEvent`/activity-event writes it caused — the same append-and-advance-atomically discipline `architecture.md`'s "Command and event flow" already requires for ordinary commands. A crash between "read the feed" and "commit the advance" leaves the cursor exactly where it was; the next tick re-reads the same feed window and reprocesses it through the same idempotency-key machinery (`idempotency_keys`, already shared by `CaseStore.append`/`updateSelection`) any resulting command would use, so a double tick after a restart produces no duplicate effect. A crash **after** the commit leaves the cursor already advanced, so a restart tick correctly sees nothing new. Either way, "the service restarted mid-tick" and "the service ticked twice in a row and found nothing" are indistinguishable from outside, which is the property that makes this survive both a Railway restart and AgentCore Runtime's 15-minute idle timeout without a special recovery path.

**Consequences.** This rules out a design where scheduling state is a queue library, a cron package, or anything whose durable record is not a row this project's own migrations own. It also means the scheduler adds no new persistence technology — it is more `better-sqlite3`/Drizzle tables, migrated the same way `runs`/`case_events`/`activity_events` are (`architecture.md` "Persistence"). See the accompanying `architecture.md` edit for the exact tables.

### 5. Authority split, extended from decisions to attention

The existing rule — "the model may propose candidate events and recommendations, it may never approve a consequential decision" — is extended, not amended, to cover a person's attention:

- **The model decides whether a change is material.** This is watch **triage**: subjective, bounded by `BudgetGuard`, produced by the vended `LLMSteeringHandler` triage agent (Decision 3). Its output is a proposed reopening (a subset of the watch's declared `reopens` obligation ids) and a plain-language note. It is a proposal, in exactly the same sense `Recommendation`/`DecisionProposal` are proposals elsewhere in this product — advisory, never self-executing.
- **The deterministic core decides whether a human is interrupted**, from facts it already computes: did the favoured option change (`scoreCaseState`'s ranking — `docs/decisions/0012-deterministic-scoring-and-insights.md`), did readiness change (`evaluateReadiness`), did a hard constraint flip (a constraint violation flag flipping on the scoreboard). These three facts are crossed with the person's interrupt policy — a new case-level setting this decision introduces, specified in full in the accompanying `product.md` edit — to produce exactly one of: interrupt (a pending `HumanInTheLoop` confirmation surfaces as something requiring attention), or stay quiet (`watch.suppressed`).
- **The model may never trigger an interruption.** There is no code path from the triage agent's output to a person's notification state. The triage note can say "this looks material" as forcefully as it wants; whether a human is actually interrupted is computed afterward, by the core, from measured before/after facts about the case — never from the model's own assessment of its own finding's importance. This is the same reasoning `docs/decisions/0012-deterministic-scoring-and-insights.md` already applies to recommendation confidence: a self-assessed figure cannot be checked, and a measured one can.

**Consequences.** A watch can fire, trigger bounded work, and change canonical case state (a reopened obligation, new evidence, a revised score) with **zero** human interruption, if the core's before/after comparison finds none of the three facts changed and the person's policy is `decision_only`. This is the whole point of the feature — most watch cycles produce `watch.checked` or `watch.suppressed`, and the rare one that changes the favored option produces a ping. It also means the core needs the "before" state to compare against, which for a watch-initiated run is the case's own state immediately before the watch's bounded work started (not, e.g., some longer-lived baseline) — the same "compare current snapshot to the snapshot one command ago" pattern `recommendation.invalidated`/`recommendation.ready` already use elsewhere in the reducer.

## Trigger kinds: push, time, query

One dispatcher, three sources of "something to check," matching `docs/hackathon-enhancements.md` §A exactly:

| Kind | What arrives | Right primitive | `bid-comparison` example |
| --- | --- | --- | --- |
| `push` | Something happens and tells the dispatcher | A listener registered against a feed; the dispatcher is notified, it does not poll | A revised bid is submitted to the `bids-inbox` fixture feed |
| `time` | Nothing happens, and that absence is the change | A scheduler tick against an injectable `Clock`, comparing a stored deadline to `clock.now()` | `bid.price_verification`'s 30-day price hold lapses |
| `query` | The source has no push mechanism and must be asked | A scheduler tick that polls a feed on an interval | A licence/insurance registry with no webhook, checked nightly |

All three feed the same dispatcher, which evaluates a deterministic, core-owned **predicate** per watch (`WatchDeclaration.predicate` — see `packs-and-routing.md`'s edit) to decide whether the trigger actually fired for this case, before triage ever runs. The predicate is deterministic and pack-declared ("a document with a newer revision than the one this case last saw," "the stored deadline is before `clock.now()`"); only whether a *fired* trigger is *material enough to act on* is the model's job (Decision 5). In fixture mode, `feed` names a time-indexed fixture (matching every other fixture tool in this product), and a `query`-kind watch's poll interval is honest fixture time, never wall-clock real time dressed up as a "check" — see the Honesty boundary section below.

## Pack declaration

A `watches[]` array on the manifest, compiled and hashed exactly like every other manifest field (canonicalization already drops `undefined` keys before hashing — `packages/packs/src/canonicalize.ts` — so a pack that declares no watches produces the identical `compiledHash` it always has, and `bid-comparison`'s existing pinned cases are unaffected until the pack is deliberately re-versioned to add them). The full shape is specified in the accompanying `packs-and-routing.md` edit; it is not reproduced in full here to avoid two documents disagreeing about field names as the design is implemented. In outline, a `WatchDeclaration` names: an id and human-readable label; its trigger `kind` (`push | time | query`); the `feed` it reads (a fixture feed id today, the same contract a real source would use later); a deterministic `predicate` describing what counts as "fired"; the obligation ids it may `reopens`; an optional `specialistId` for the bounded work; a tightened `budget`; and a `defaultInterruptPolicy`.

## New runtime and activity events

Four new event names, matching `docs/hackathon-enhancements.md` exactly, split across the existing public/runtime-only boundary (`architecture.md`'s `PublicActivityEvent` versus `debugging-and-observability.md`'s `RuntimeDebugEvent`):

| Event | Visibility | Why |
| --- | --- | --- |
| `watch.checked` | **Runtime-only.** | A tick that found nothing new is proof-of-liveness, not something worth a person's attention — and it is by far the highest-frequency event this feature produces. Making it public would force the consumer stream to invent a "collapse repeated quiet events" UI rule it does not otherwise need; keeping it runtime-only means the freshness indicator (`product.md`'s new "Current as of…" line) is derived by *reading* the `watches` table's `lastCheckedAt` columns directly, not by counting activity events. |
| `watch.fired` | **Public.** | The predicate matched — bounded work is starting or has run. Worth showing even when the triage verdict turns out to be "not material," because "the agent noticed something and looked into it" is itself the vigilance claim this feature exists to prove. |
| `watch.triaged` | **Public.** | The model's triage verdict, rendered as a structured fact (`material: boolean`, a plain-language note citing the changed document) — not raw reasoning. This is the same class of disclosure `goal.validation_failed`/`intervention.guide` already make public: a validated, source-linked output, never chain-of-thought. |
| `watch.suppressed` | **Public.** | Fired and triaged material work happened, and the core's before/after comparison found nothing that crosses the person's interrupt policy. Load-bearing: this is the event that makes "it noticed and chose not to bother you" a fact a person can see rather than a claim the product makes about itself. See the accompanying `product.md` edit for exactly where it surfaces without becoming noise. |

A watch-initiated run that *does* cross the interrupt policy does not mint a fifth event type. It reuses the existing `intervention.confirmation_required` public event (`architecture.md`'s `PublicActivityEvent.type`), now correlated to a run whose `InterventionEvent.handler` is `'HumanInTheLoop'` instead of `'ConsequenceGuard'` (Decision 1) — the person-facing fact ("something needs your attention") is identical in shape to the foreground confirm case; only the mechanism that produced it differs, and that mechanism is developer-view detail, not a new consumer-facing event vocabulary.

## Honesty boundary

A real scheduler over a fixture feed is honest, on the same reasoning every other fixture tool in this product already rests on: every specialist, every tool call, every piece of "external" evidence in a deterministic Sift run already comes from a checked-in fixture, and nobody has ever called that dishonest. What must be real is the *loop* — an actual `Clock`, actual ticks, actual predicate evaluation, actual bounded work, actual events — not the data source behind it.

**Rule.** Copy anywhere in the product must state what is being checked and where that data came from. It must never imply a live external connection that does not exist.

| Compliant | Non-compliant | Why |
| --- | --- | --- |
| "Checked the bid inbox fixture · 2 min ago (fixture time)" | "Monitoring your inbox" | The second implies a live mailbox connection. There is none. |
| "Watching 3 things in this case" | "Watching your email" | "This case" names a bounded, real scope; "your email" claims access the product does not have. |
| "Current as of 2 min ago (fixture clock)" | "Current as of 2 min ago" (with no qualifier, in fixture mode) | A relative timestamp with no clock qualifier reads as wall-clock time to a person unaware the demo runs on injected time. |
| "Licence registry check (fixture) — no change" | "Registry check — no change" | Omitting "(fixture)" lets the sentence be read as a live registry query, which it is not, in the demo build. |

Fixture time is always labelled as fixture time. The environment variable `SIFT_DEMO_PACING_MS` (`apps/agent/src/config.ts`, an integer 0-2000 defaulting to 0, consumed by `bid-comparison-engine.ts` and the other engines) is the existing precedent for a demo-shaping knob that changes pacing without changing events, counts, or ordering. Fixture *time* is a different thing from pacing and needs its own rule, stated here for the first time: wherever the scheduler's clock is a fixture clock, every timestamp derived from it is labelled as fixture time in the UI, and no copy may imply a live external source that does not exist. The exact UI copy contract is stated in full in the accompanying `product.md` edit.

## Determinism and testing

A scheduler cannot be tested with `sleep`. Three mechanisms, all already precedented elsewhere in this codebase:

1. **An injectable `Clock`.** The scheduler takes the same `{ now(): string }` port every other deterministic module in `packages/core` already takes — see "What 'unify the Clock port' actually means here" below for exactly which one. A test advances a fake clock and calls the dispatcher's tick function directly; no wall-clock time passes during a test run.
2. **A dev-only "advance fixture time" control**, for `pnpm test:e2e`/`pnpm test:journey`-style browser tests, where a fake `Clock` cannot be swapped into a running server process from the browser side the way a unit test swaps one into a function call. This is a bounded, labelled debug control (gated the same way `SIFT_DEBUG_ENABLED` gates the Runtime Inspector — never present in a build where fixture time could be mistaken for real time) that advances the server's injected clock and triggers one dispatcher pass, so a Playwright test can drive "the price hold lapses" deterministically instead of waiting.
3. **Idempotent ticks** (Decision 4) mean a test can call the dispatcher twice for the same watch and assert the second call is a no-op, which is itself the regression test for "does a restart replay correctly."

See the accompanying `testing.md` edit for the exact new `ScenarioAssertion` kinds this adds (`watch_fired`, `watch_triaged`, `watch_suppressed`) and where they sit in the existing declarative scenario DSL.

### What "unify the Clock port" actually means here

The proposal that motivated this ADR described two duplicate `Clock` interfaces needing unification before a scheduler could be built. Reading `packages/core/src/*.ts` directly (this ADR's Context section) found three duplicates, not two — `attributes.ts`, `evidence.ts`, and `policy.ts` — and, more importantly, found that a canonical fourth file, `ports.ts`, already exists, already re-exports as `packages/core`'s barrel `Clock`/`IdGenerator`, and already carries a header comment stating it is "the actually-canonical port pair going forward" for new code. A prior integration pass made a deliberate, recorded decision (`ports.ts`'s own header comment, corroborated by `docs/build-log.md`) to leave the three older duplicates in place rather than risk regressing files that were already green and fully tested.

This ADR does not reopen that decision or ask a later task to collapse the three duplicates — that is unrelated cleanup with its own blast radius, and rewriting three already-tested files the week of a hackathon deadline for no functional gain is exactly the kind of risk Decision 2 above declines to take for Cedar. What this ADR **does** require: the scheduler, being new code, imports `Clock`/`IdGenerator` from `packages/core/src/ports.ts` (via the package barrel, `import type { Clock } from '@sift/core'`) — the same import `run-service.ts` already uses — and never declares a fourth local copy. The scheduler is new-code adoption of the already-canonical port, not a unification project.

## Prerequisites this feature needs that do not exist yet

None of these are Standing Watch itself; all of them are load-bearing for it and must land first:

1. **Per-case run serialization.** Nothing today prevents two runs on one case interleaving. A watch-initiated run and a person's click racing on the same case is the first failure this feature makes reachable that was previously only theoretical. Needs a per-case queue (serialize writes to one case) with a global concurrency cap (bound total background work across cases).
2. **A `GET /api/cases` summary endpoint and a global event stream.** SSE today is exactly `/api/cases/:caseId/events` — per case, nothing else. A case list showing "3 watched, 1 needs you" needs both a summary read (every case's id, title, pack, and watch/attention state in one response) and a way to learn when any of them changes without opening N per-case connections.
3. **Read markers.** "Since you were away" needs to know what a person has already seen. Nothing records it today. Given this product's explicit, unchanged scope cut against accounts/multi-user (`product.md`, "Explicit scope cuts"), a read marker is one row per case (`last_seen_activity_sequence`), not one row per case per user.

These three are ordered before any watch-specific work in the accompanying edits' sequencing notes, because Standing Watch's UI claims (freshness, digest, case list) are unbuildable without them, and building them for a single-case, single-watch minimum slice first is how a three-day minimum slice (`docs/hackathon-enhancements.md`'s own effort estimate) stays three days instead of becoming five.

## Consequences

- `bid-comparison` gains an optional `watches[]` field; `car-purchase` and `home-energy-guardian` are untouched, and their `compiledHash` values are provably unaffected by this ADR (canonicalization drops undefined keys).
- Two new SQLite tables (`watches`, `pending_interrupts`) plus one new column-light table (`read_markers`), migrated the same way every existing table is. No new persistence technology.
- Four new event names in the public/runtime split (three public, one runtime-only), and no new public event for the interrupt case itself — it reuses `intervention.confirmation_required`.
- `ConsequenceGuard` and its scenario coverage are untouched. A second intervention handler (`HumanInTheLoop`) is added for a run class (`origin: 'watch'`) that does not exist in the product yet, so nothing currently green can regress from this change alone.
- Cedar and A2A ship as proven-but-unwired spike evidence; neither is a dependency of the minimum slice.
- The scheduler is new code, not a refactor of existing `Clock` usage; the three pre-existing duplicate `Clock` declarations are explicitly left alone by this decision.
- Three prerequisites (run serialization, case summary/global stream, read markers) must land before the first watch can ship a truthful UI, and are treated as their own ordered work, not folded silently into "the watch task."

## Alternatives considered

- **Route background confirmation through `ConsequenceGuard` too, with a fixture-mode-only `resolveConfirmation` standing in for a human.** Rejected: this is what the existing hackathon-enhancements audit calls "staged autonomy" — a confirm that always auto-resolves in the exact case (no live consumer) where a real pause matters most. It would also not survive a process restart, since `ConsequenceGuard`'s confirm is a synchronous in-process pause, not a persisted interrupt.
- **Cedar as the default deny mechanism, replacing `ScopeAuthorization` everywhere.** Rejected for this build (Decision 2); recorded as a revisit condition below, not abandoned.
- **A free-floating `setInterval` per watch, held in server memory.** Rejected (Decision 4): does not survive a restart, cannot be tested without real elapsed time, and cannot be idempotency-keyed the way a row can.
- **`MemoryManager` (spike 5) as the mechanism for "what the person has already seen," instead of an explicit read marker.** Rejected for the minimum slice: `TestMemoryStore` recall is lexical (token-overlap), not semantic — a query sharing zero tokens with a stored entry returns zero results and fails open (silently injects nothing), which is a subtle, hard-to-notice failure mode for a feature whose entire point is "prove the agent noticed." An explicit `last_seen_activity_sequence` row is deterministic and trivially testable. Recorded as a revisit condition below, not ruled out permanently — a richer cross-session "what has this household told Sift before" story is a plausible later use of `MemoryManager` unrelated to read markers specifically.
- **A2A (spike 3) as the transport for the background triage/work agent**, making "numerous agents in the background" literal by running the watch agent as its own addressable network service. Rejected for the minimum slice: the SDK itself logs its experimental status at import time ("breaking changes in the underlying sdk may require breaking changes in this module"), and the minimum slice needs zero network hops to prove the vigilance claim — an in-process triage agent invoked by the dispatcher demonstrates the same authority split with strictly less surface area to get wrong this week.
- **Per-watch interrupt-policy overrides**, rather than one case-wide setting. Rejected for the minimum slice as unnecessary complexity for a single-watch demo; the case-wide setting is simpler to build, simpler to explain on camera, and does not foreclose a later per-watch control (a case-wide policy is a special case of a per-watch one, not a competing design).

## Revisit conditions

- **Cedar** becomes the default when a second background-tool-policy surface needs a genuinely different principal/action shape than an allowlist can express cleanly, or when preparing specifically for AWS-judge review makes "policy as data" worth the rewiring risk on its own merits — not before the WebMCP-deadline build is frozen (`CLAUDE.md`'s "Current execution authority").
- **A2A** becomes worth adopting if a later demo beat specifically needs to show "an agent running as its own addressable service," which the minimum slice does not need to claim.
- **`MemoryManager`** is worth revisiting once read markers alone prove insufficient for a richer "what has this household told Sift before, across cases" story — a different feature than the digest this ADR specifies, which read markers fully cover.
- **Per-watch interrupt policy** is worth building the moment a demo needs to show two watches on one case with genuinely different attention needs (e.g., "ping me if the price changes, but never bother me about a routine registry check").
